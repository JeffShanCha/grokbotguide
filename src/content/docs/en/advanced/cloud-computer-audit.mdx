Use a resource inventory, connectivity checks and recovery plan rather than treating one author's machine as a plan guarantee.

The source examines CPU, memory, storage and tunnels. This audit replaces fixed-resource and uptime assumptions with environment checks.

## Scenario and input

Synthetic goal: a test page reachable only by its owner, with no production customer traffic.

## 1. Inventory resources read-only

Record OS, CPU and cgroup limits, memory, mounts and tools with a timestamp rather than generalizing them to every plan.

## 2. Define the service boundary

Specify private or public access, streaming, WebSocket, persistence and authentication requirements, testing each protocol separately.

## 3. Evaluate the tunnel

Choose a private or protected test route and check current vendor limits. A reachable temporary tunnel is not an uptime guarantee.

## 4. Test lifecycle behavior

Record the effects of closing the client, idling, software updates and a computer rebuild. Autostart scripts still need recovery tests.

## 5. Choose the workload from evidence

Use the environment experimentally when tests pass; assess availability, backups and appropriate hosting for critical services.

## A synthetic acceptance fixture

audit.csv: cpu_limit, memory_limit, disk_mount, network_path, sleep_test, restore_test. Do not add capacities for directories on the same filesystem.
