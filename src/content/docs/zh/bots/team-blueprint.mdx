## 场景与输入

合成目标：每周交一份内容周报，尚无稳定的采集流程。

## 1. 收敛一个结果

让用户选择一个近期交付目标，并明确成功样例、时间和不做的范围。

## 2. 先写角色草案

每个角色只有一份主要产物，列职责、输入、停止点和接手人；角色名不代替输出标准。

## 3. 检查教学模板

读取模板包含什么以及是否附带外部应用或自动化；未读到的描述不直接当成可运行配置。

## 4. 按任务核对应用

列出必要连接器、账号和只读验证；作者推荐的插件名称不等于已安装、可用或已授权。

## 5. 确认后再扩角色

先手动跑通一份周报，再决定保存模板或增加专员；创建、群聊和定时都与规划分开确认。

## 一份合成验收样例

roster.csv：role、input、deliverable、reviewer、trigger。起步只设资料整理员和本人审阅，不默认同时创建出海站与视频团队。

## 视频补充：给发布统筹一份可核对的 X 长文草稿

59 秒的录屏不是建团队教学，而是团队中“发布统筹”岗位的一次工作演示：把本地 Markdown 和图片送入 X Articles 草稿。它补出一项正文与配图未描述的流程。

| 时间点 | 画面证据 | 交付含义 |
| --- | --- | --- |
| 00:00–00:14 | Bot 报告使用 `x-article-publisher`，用户提供本地 Markdown 路径 | 先明确输入文章和配图；技能已安装是画面中的自述 |
| 00:14–00:25 | 出现本机命令授权，文件复制有失败后重试 | 命令授权和素材复制是独立环节，需要分别核对 |
| 00:25–00:43 | 用户进入 Bot 电脑浏览器完成 X 登录与验证，再交还控制 | 网站会话需要本人处理；安装连接器不能代替这次登录 |
| 00:43–00:58 | Bot 返回草稿链接、标题、封面和图片结果：10 张成功 8 张 | 草稿已有，但缺 2 张图；画面没有正式发布完成的证据 |

### 把这个岗位写成五步交付

1. **交素材清单。** 给出 Markdown 的确切路径、标题、封面和应有图片清单，约定本轮只生成草稿。
2. **核对执行条件。** 原演示使用第三方技能和浏览器自动化；现已取得作者仓库并静态核对关键脚本，具体文件、版本和新增验收点见下方源码补充。复现前仍须核对命令、位置、profile 与文件范围。
3. **检查素材是否齐全。** 文件拷贝失败要报缺项；“已复制 10 张”不能替代编辑器中的上传结果。
4. **由本人完成登录。** 按电脑接管卡片登录并处理验证，再交还给 Bot；这是[官方接管流程](https://cursor.com/docs/grok-bot/work)，本文不复述画面里的账号或验证码。
5. **按草稿清单验收。** 回执包含草稿链接、标题、封面、应有与实际图片数、缺图名称和未完成项。像录屏的 8/10，应先补图并重新预览；最终发布另作明确决定。

## 源码补充：把发布统筹的草稿回执核对到文件

已取得作者的 [xaiwind/x-article-publisher](https://github.com/xaiwind/x-article-publisher/blob/6cd2f1b752afe966c00bb803c1a1c5eb7a1085d4/README.md)，固定在 `6cd2f1b`。仓库账号关联的 X 用户为 @xaiwind，系统 Chrome、`playwright-core`、跨助手技能目录与草稿输出均和录屏相符；**没有证据证明录屏运行的恰好是这个 commit**。`LICENSE` 声明 MIT，并保留上游传承说明。

### 按源码落实五步

1. **固定工具与输入。** 记录仓库、commit、Markdown 路径、标题和配图清单。入口是 [auto-publish.js](https://github.com/xaiwind/x-article-publisher/blob/6cd2f1b752afe966c00bb803c1a1c5eb7a1085d4/auto-publish.js#L22-L51)，依赖见 [package.json](https://github.com/xaiwind/x-article-publisher/blob/6cd2f1b752afe966c00bb803c1a1c5eb7a1085d4/package.json)。账号还须实际具备文章编辑入口，资格按 [X 官方说明](https://help.x.com/en/using-x/articles)核对。
2. **先整理图片路径。** [payload.js](https://github.com/xaiwind/x-article-publisher/blob/6cd2f1b752afe966c00bb803c1a1c5eb7a1085d4/payload.js#L77-L141)优先解析文章目录中的文件，也会查找 Obsidian 附件；这个入口明确拒绝 HTTP 远程图片。macOS 的 PNG/JPEG 达到压缩阈值时才尝试 `sips`，其他平台会跳过，不能承诺所有图片都已压缩。
3. **明确浏览器会话范围。** 首次用有界面模式由本人登录，后续才考虑 `--headless`；`--profile` 指定独立会话目录。源码会尝试关闭占用同一 profile 的实例并清理锁文件，复现前应确认对应窗口与执行范围，不能将它描述为只读检查。本文没有运行该入口。
4. **逐项判定回执。** [xpage.js](https://github.com/xaiwind/x-article-publisher/blob/6cd2f1b752afe966c00bb803c1a1c5eb7a1085d4/xpage.js#L725-L854)分别累计 `imgOk`、`imgFail`、`atomicFail`，图片或代码、表格插入失败可能降级为文字。函数末尾仍可能返回 `ok: true`；因此总开关成功不代表正文图片和格式齐全。
5. **重新打开草稿验收。** [入口的收尾逻辑](https://github.com/xaiwind/x-article-publisher/blob/6cd2f1b752afe966c00bb803c1a1c5eb7a1085d4/auto-publish.js#L189-L220)会等待自动保存、清理标记并输出草稿 URL；没有独立回读服务端内容的验收步骤。拿到链接后再核对标题、封面、图片顺序、数量、格式降级和残留标记，最后由本人决定发布。

例如一份**合成回执**：`ok=true`，但 `summary.imgOk=8`、`summary.imgFail=2`，应记“草稿部分完成，待补图”，不能记“可直接发布”。这解释了录屏为什么已有链接仍需补图；它不是本站修复了作者那两张图片的证据。
