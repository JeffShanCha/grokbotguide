分别验证飞书应用、用户授权和目标文档权限，打通群消息到 Webhook 的路径，再做来源到草稿的单条试跑。

原文用总管、情报官、内容官组织飞书团队。配图显示所谓 iMessage 渠道是一条例行任务的名称，实际作用是飞书群到 Webhook 的桥接。

## 场景与输入

合成材料：一条已读的公开 X 文章和一个仅供测试的飞书文档。

## 1. 画出消息路径

注明飞书群、应用机器人、转发程序、Webhook Routine 和 Grok Bot；群自定义 Webhook 与可订阅消息的应用机器人分开。

## 2. 检查三层权限

核对应用范围、用户或 CLI 身份、目标文档共享权限；缺一就停在对应层，不扩大到整个企业空间。

## 3. 只跑一条情报

把允许读取的来源整理为带链接和读取范围的记录，内容官只读这条记录，不自行补造素材。

## 4. 桥接时保留任务身份

为群消息生成任务编号，忽略机器人自身回声并防重复；200 与任务完成分别回查。

## 5. 在测试文档交稿

写入来源、草稿和待确认项后由本人核对；生产文档、群通知和公开发布在验证后另按授权执行。

## 一份合成验收样例

handoff.csv：source_url、read_scope、topic_status、draft_doc、reviewer。App 能收消息、CLI 已登录、文档允许写入分别有测试结果。

群消息能追到一份来源和一份稿件；没有自触发循环；权限失败不被写成成功。
