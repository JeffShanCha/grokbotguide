## 场景与输入

合成输入：request_id=KB-001、source_url=https://example.com、kind=link。

## 1. 定义知识库产物

先确定允许写入的测试目录和必需字段，要求短摘要、原链接、作者和实际读取范围。

## 2. 创建受控触发草案

由负责 Bot 的 Routine 接收 JSON，核对 POST 地址与 Bearer 标头；凭据不写进公开快捷指令示例。

## 3. 配置手机发送端

快捷指令使用获取 URL 内容、POST、JSON 请求体和授权标头；从分享输入取得链接，文本菜单作为另一个输入入口。

## 4. 检查接受与完成

HTTP 200 只记录已接受；回到 Bot 对话查看来源读取、产物路径和失败项。视频没有转录或看图时分别注明。

## 5. 用异常样本复测

验证正常链接、重复编号和不可访问链接；失败不写成空内容成功，确认后再连接正式知识库。

## 一份合成验收样例

inbox.csv：request_id、source_url、read_status、stored_path、error。重复提交 KB-001 只产生一条记录；不可读网页保留失败原因。

## 视频补充：两种手机入口与完成状态

两段录屏没有新增一套知识库架构，而是补清已有快捷指令在手机里的操作位置。它们只展示前端提交，均没有出现最终入库回执。

### 视频一：抖音分享入口（12.23 秒）

1. 在内容页点分享（00:00–00:03）。
2. 进入“更多”，打开系统分享面板（00:03–00:06）。
3. 选“发送给知识库 Bot”（00:06–00:07）。
4. 返回原内容继续播放（00:07–00:12），另到 Bot 对话核对这次请求及产物，不能仅凭页面返回就记入库完成。

这是原方法 `a11-m02` 的入口细节。录屏原声属于被分享的第三方视频，不是 Grok Bot 操作讲解；自动识别覆盖全段，本文没有转录该作品。

### 视频二：微信复制后输入（16.97 秒）

1. 在文章右上菜单复制链接，确认“已复制”（00:00–00:04）。
2. 唤起快捷指令，选择“收录到知识库”（00:04–00:06）。
3. 在“请输入要收录的链接”框粘贴网址（00:06–00:12）。
4. 提交后回到文章继续阅读（00:12–00:17），再核对 Bot 的读取状态、摘要与目标路径。

这是原方法 `a11-m03` 的操作细化。画面不能确定它由侧边按钮还是其他入口唤起，因此不把“绑定操作按钮”写成录屏已验证的前提。音轨经全程分析为数字静音。

### 接入现有验收步骤

让两条入口提交同一条合成测试链接，分别保存 `entry=share_sheet` 与 `entry=manual_link`、请求编号和返回时间。已有 `request_id` 去重规则照常执行。服务器回执另外记录“已接受／已读来源／已存入”；[官方说明](https://cursor.com/help/grok-bot/routines)中的 HTTP 200 只表示接收并开始运行。手机端演示不能证明服务端完成了整理、去重或写入。

## 作者补充：同一 Bot 的多个 Webhook 用途

铁柱补读的 [作者回复](https://x.com/cgnot996/status/2111499978728448348)说明，同一 Bot 可以接收多条带不同指令的 Webhook。这是作者对入口组织方式的补充，没有提供完整快捷指令动作或本轮入库回执，不能据此确认手机端的具体唤起方式。

据此可把本站验收表细化为三步：

1. 先列出输入类型与对应处理指令，例如链接摘要或文本笔记，再记录各自对应的入口，避免把所有请求当成同一种内容。
2. 为每条入口分别核对 Routine、请求字段和目标目录。若沿用原图的 `info` 或使用本站练习的 `request_id`、`source_url`，接收端解析规则必须同步，不能只改手机请求体。
3. 用同一条合成内容分别验证路由、去重和完成回执。多一个入口不代表已有读取、整理或入库成功的证据。

上面三步是本站根据作者说明整理的配置与验收建议，未运行真实 Webhook。作者另提的 SDK 或浏览器插件不替代这套手机快捷指令；本轮未取得可确认归属的完整安装与入库材料。
